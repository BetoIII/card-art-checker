Card Art Checker API

Submit a card design, get back a structured compliance verdict against the Visa brand rules — which checks failed, where on the art, and whether the design can ship.

Overview #

A check is a visual review: a Claude agent inspects the art against 18 Visa rules and returns a decision. That takes 100–160 seconds, so no endpoint returns a verdict synchronously. Every integration has the same four beats.

01
Submit
POST the art with ?async=1.
02
Store the runId
Returned immediately. Your handle on the run.
03
Wait
The analysis runs in the background.
04
Read the result
Poll, or have it pushed to your webhook.

The numbering above is a real sequence — each step depends on the one before it, and a run cannot skip one. Everything else in this reference describes the shape of one of those four calls.

Base URL. https://card-art-checker.vercel.app

Use the stable alias, not the per-deploy …-<hash>.vercel.app URLs — those change on every push.

Quickstart #

Submit a virtual card design and read the verdict.

Submit 
curl -X POST "https://card-art-checker.vercel.app/api/card-check?async=1" \
  -H "Authorization: Bearer $CARD_ART_CHECKER_SECRET" \
  -F "file=@card.png" \
  -F "cardType=virtual" \
  -F "reference=cardArtForm_01HX9"

# → { "ok": true, "queued": true, "runId": "msqz4i4j-6fa7c9",
#     "projectId": null, "reference": "cardArtForm_01HX9",
#     "cardType": "virtual" }
const form = new FormData()
form.append("file", new Blob([artBuffer], { type: "image/png" }), "card.png")
form.append("cardType", "virtual")
form.append("reference", cardArtForm.id)

const res = await fetch(`${CARD_ART_CHECKER_URL}/api/card-check?async=1`, {
  method: "POST",
  headers: { Authorization: `Bearer ${CARD_ART_CHECKER_SECRET}` },
  body: form,
})

const { runId } = await res.json()
// Store runId on the row — it is how you find the verdict later.
Read the verdict 
curl -H "Authorization: Bearer $CARD_ART_CHECKER_SECRET" \
  "https://card-art-checker.vercel.app/api/result/msqz4i4j-6fa7c9"

# 404 while the run is still in flight — that is the normal answer.
# 200 → { "runId": "…", "count": 1, "results": [ … ] }
const res = await fetch(`${CARD_ART_CHECKER_URL}/api/result/${runId}`, {
  headers: { Authorization: `Bearer ${CARD_ART_CHECKER_SECRET}` },
})

if (res.status === 404) return // still running, try again later

const { results } = await res.json()
const [result] = results

if (result.status === "error") return           // the checker broke — retry
if (result.outcome === "requires_changes") {
  reject(result.summary, result.blocking_failures)
}

Polling works, but webhooks are the recommended path — they cost you nothing while a two-minute run is in flight.

Authentication #

One shared secret guards every server-to-server endpoint. Send it either way:

Headers 
Authorization: Bearer <secret>
x-webhook-secret: <secret>

Ask Beto for the value — it is not published here. The same secret reads results, so a caller that may start a check may read its verdict.

Authentication does more than gate access. It is what separates a server-to-server caller from the browser upload page. Authenticated callers may omit projectId and use ?async=1; anonymous ones may not.

If your calls behave like the browser path — streaming back an event stream, demanding a projectId — the secret is not arriving.

Submit a check #

POST /api/card-check?async=1 Bearer token

Send the art as multipart/form-data. With ?async=1 the response returns as soon as the file is parsed and the analysis continues in the background. Without it you get a Server-Sent Events progress stream instead — that path exists for the browser playground; don't use it from a server.

Body fields #

FieldTypeDescription
file file Required The card art. PNG for virtual submissions.
cardType "virtual" | "physical" Optional Inferred from the filename when omitted. Send virtual explicitly — back-office art always is.
reference string Optional Your own correlation id, e.g. a cardArtForm.id. Comes back on trigger.reference. Sanitized to [A-Za-z0-9._-], 64 chars max.
projectId string Optional Rocketlane project id. Omit it unless you have one — when present it must resolve in Rocketlane or the run fails. Required for unauthenticated callers.
callbackUrl string Optional Push the result here instead of polling. Allowlist-gated — see Webhooks.
backFile file Optional Physical submissions only. Rejected on a virtual submission.
slackDelivery boolean Optional Defaults to true. Only affects the Rocketlane-driven flow.

Responses #

200  Queued

The file was accepted. Store runId — it is the only handle on the run.

200 application/json 
{
  "ok": true,
  "queued": true,
  "runId": "msqz4i4j-6fa7c9",
  "projectId": null,
  "reference": "cardArtForm_01HX9",
  "cardType": "virtual"
}

400  Never started

A runId still comes back, so the attempt stays traceable in the admin dashboard.

400 application/json 
{ "error": "No file uploaded", "runId": "msr0w4np-1eoerz" }

Other error values:

  • Missing projectId — unauthenticated callers only.
  • Invalid cardType "foo" — must be "virtual" or "physical"
  • Could not infer card type from "art.bin" — pass cardType=virtual|physical explicitly
  • Multipart parse timed out — the body took longer than 30s.
  • backFile is only valid for physical submissions

A wrong content type returns 400 with a plain-text body: Bad request: expected multipart/form-data.

Fetch a result #

GET /api/result/{runId} Bearer token

One run can analyze several files, so this returns every stored result for the run — each with its own attachment_id.

StatusBodyMeaning
200 { runId, count, results[] } Done. See the result object.
404 { error, runId, hint } Still running, or unknown run. This is the normal answer while waiting — not an error.
400 { error: "Malformed runId" } Run ids look like msqz4i4j-6fa7c9.
401 Unauthorized (text) Bad or missing secret.
502 { error: "Result lookup failed" } The result store could not be read. Retry.

Every run also publishes a resultUrl — a public blob URL that needs no auth to read. It is unguessable, but treat the URL itself as the secret.

Rocketlane trigger #

POST /api/card-art-check?projectId={id} Bearer token

The project-keyed entry point, driven by a Rocketlane Form completed automation. Instead of a file upload it takes a project id, and pulls the art from the attachment anchors in the payload — <a data-attachment-id="12345">. One field can carry several files, and each is analyzed separately.

Reach for this only if you are wiring up Rocketlane. Everything else should post the file directly.

InputDescription
projectId Required Numeric Rocketlane project id. Query string wins over the JSON body. Routes Slack delivery and the report path.
attachment ids Required Read from data-attachment-id="…" anchors anywhere in the payload. An explicit attachmentId field also works for manual calls.
cardType Optional Applies to every attachment in the request. .ai and .eps always run physical regardless.
callbackUrl Optional Allowlist-gated, same as /api/card-check.

Resolving and downloading attachments happens before the response, so the status code tells you whether the art was retrieved: 200 { ok, queued, projectId, runId, downloaded[], failed[] } · 400 missing project id or no attachments found · 502 every download failed, nothing was analyzed.

Manual trigger 
curl -X POST "https://card-art-checker.vercel.app/api/card-art-check?projectId=12345&attachmentId=67890" \
  -H "Authorization: Bearer $CARD_ART_CHECKER_SECRET"

Webhooks #

The recommended way to receive a verdict — no polling, no idle connection. It needs a receiving route on your side and one config change on ours: either RESULT_WEBHOOK_URL pointed at your endpoint, or your host added to RESULT_WEBHOOK_ALLOWED_HOSTS so a per-request callbackUrl is honored.

What arrives #

POST your endpoint 
Content-Type: application/json
User-Agent: card-art-checker/1.0
X-Card-Art-Signature: sha256=<hex>
X-Card-Art-Timestamp: <unix seconds>
Envelope 
{
  "schema_version": "1.0",
  "event": "card_art_check.completed",
  "run_id": "msqz4i4j-6fa7c9",
  "attachment_id": null,
  "occurred_at": "2026-08-13T04:32:34.023Z",
  "data": { }
}

event is card_art_check.completed or card_art_check.failed. data holds the result object.

Verifying the signature #

HMAC-SHA256 over {timestamp}.{rawBody}. The timestamp is inside the signed material, so a captured request cannot be replayed with a fresh one.

verify.ts 
import { createHmac, timingSafeEqual } from "node:crypto"

function verify(rawBody: string, headers: Record<string, string>, secret: string) {
  const ts = headers["x-card-art-timestamp"]
  const expected = "sha256=" + createHmac("sha256", secret)
    .update(`${ts}.${rawBody}`)
    .digest("hex")

  const a = Buffer.from(expected)
  const b = Buffer.from(headers["x-card-art-signature"] ?? "")
  return a.length === b.length && timingSafeEqual(a, b)
}

Verify against the raw body, before JSON parsing. Re-serializing changes the bytes and the signature will never match.

Field notes #

FieldNotes
outcome The review decision. Branch on this.
status Legacy top-level state: pass · fail · error. approved_with_notes collapses to pass, so it erases the distinction you care about — don't decide on it. error means the run broke; see failures.
checks[].id The contract. Bind to this.
checks[].name Display text the model may reword. Never match on it.
checks[].marker Normalized 0–1 coordinates on the art — {x: 0.84, y: 0.82} is lower-right. Absent when the issue isn't locatable. Enough to pin the problem on a preview tile.
counts Only non-zero statuses appear as keys.
blocking_failures Check ids that are fail and blocker. Empty means nothing blocking.
colors Extracted from the art. Compare against the colors the tenant declared.
unmapped_checks Should always be []. Non-empty means our prompt and catalog have drifted — nothing is dropped, but tell us.

Enums #

Closed sets 
type Outcome  = "approved" | "approved_with_notes" | "requires_changes"
type Severity = "blocker" | "required" | "advisory"
type Status   = "pass" | "fail" | "warning" | "not_submitted" | "unverified" | "estimated"

warning is a real and common state — a borderline measurement that didn't fail. Treat anything that isn't pass as "not clean", but reject only on blocking_failures.

Technical checks #

Four structural measurements ride along in tech_checks: dimensions, file_format, dpi, and bleed_zone.

dpi here means calculated DPI ≥ 72, not "declared density equals 72" — a PNG declaring 300 DPI passes this check.

This service runs after your own structural validation, not instead of it. If you already reject non-PNG or wrong-sized art before submitting, these four should always pass — ignore them for the review decision.

A failure means the two layers disagree about the same file. That is worth an alert, not a rejection.

Errors & failures #

A run that never produced an analysis still publishes a result, so "this card has problems" stays distinguishable from "the checker fell over".

Never reject a design on a failure result. Leave the submission open and retry.

Failure result 
{
  "schema_version": "1.0",
  "run_id": "msr0w4np-1eoerz",
  "card_type": null,
  "generated_at": "2026-08-13T04:12:09.114Z",
  "outcome": null,
  "status": "error",
  "error": { "code": "function_timeout", "message": "", "step": "visual" },
  "project":    { "id": null, "name": null },
  "submission": { "file_name": "art.png" },
  "trigger":    { "source": "api", "endpoint": "/api/card-check", "reference": "cardArtForm_01HX9" }
}

The cheapest discriminator is status === "error". A failure result carries no checks, counts, summary, or blocking_failures at all, and outcome is null. card_type is null when the run failed before the type was resolved.

Limits #

Run duration100–160s typical. The function ceiling is 300s; the pipeline self-limits at 280s so it degrades rather than dying mid-step.
Results per runOne per analyzed file. A run covering several attachments returns several results, each with its own attachment_id.
Virtual onlyPhysical results carry schema_version: "0-internal", are never pushed to webhooks, and their enums may change without notice.
Multipart parse30s. A slower upload fails with Multipart parse timed out.
Report URLsPublic and permanent. Unguessable, but unauthenticated — don't put one anywhere you wouldn't put the report itself.
